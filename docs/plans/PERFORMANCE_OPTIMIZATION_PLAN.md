# BOO 低配置电脑性能优化方案

> 2026-07-27 更新：本文关于“保持 PAK 全量 PNG 缓存”的前提已被新的实测结论替代。PAK/JPK 素材优化请以 `ARCHIVE_DIRECT_PREVIEW_PLAN.md` 为准。

> 分析日期：2026-07-19  
> 当前扩展版本：V4.1.9  
> 原则：保持 PAK 全量缓存和空白槽，不改成按需解压

## 1. 结论

当前卡顿的主要原因不是 JSON 数据文件，也不是数据库表格一次渲染太多行。命令数据总计不到 400 KiB，单次解析耗时很低；数据库 Webview 也已经分页到每页 50-200 行。

真正的高成本集中在四处：

1. 扩展激活时立即做全工作区扫描、全量代码审查、PAK 自动缓存和 M2 守护进程启动。
2. SQLite 虽然分页显示，底层仍把完整数据库载入 `sql.js` 内存。
3. 每次改单元格都会备份、导出并重写整个 SQLite 文件。
4. PAK 全量解压、PNG 编码和大量 Webview 消息仍运行在扩展宿主主线程。

优化顺序应先处理“用户没打开功能也会发生的工作”，再处理数据库写入和 PAK 后台计算。

## 2. 已确认的瓶颈

### 2.1 激活范围过大

`package.json` 包含 `onLanguage:plaintext`。用户打开任意普通文本文件，都可能激活整套扩展。

激活后会立即：

- 扫描工作区全部 `.txt`，收集 HUMAN/GUILD 声明。
- 再扫描 `Envir` 全部 `.txt` 并执行全量代码审查。
- 自动检测并补齐需求 PAK 缓存。
- 预启动 M2Reloader 常驻进程。

这些任务发生在用户尚未打开补丁管理、代码审查或执行重载之前，是启动卡顿的最高优先级根因。

### 2.2 补全和语义着色重复全表扫描

- GOM 每次补全最多遍历约 711 个结构化命令。
- GEE 每次补全最多遍历约 1248 个结构化命令。
- 悬停使用数组或对象逐条查找。
- 文档每次修改后，块上下文缓存会重新遍历整个文件。
- 语义着色会重新遍历全部行，并为每行创建覆盖数组。

普通小脚本影响有限，但长脚本连续输入时会放大。

### 2.3 PAK 主线程与消息压力

PAK 首次缓存会：

- 同步读取完整 PAK。
- 逐图解压、转 RGBA、编码 PNG、同步写盘。
- 每 20 张图片上报一次进度。
- 最后把所有素材元数据和 URL 一次发送到 Webview。

主素材列表已经实现虚拟滚动，这是正确的。仍需处理：

- 按钮选择和特效选择弹窗会为全部素材创建 DOM。
- 进度更新会频繁触发侧栏消息和重绘。
- Webview 收到的每条素材还包含不需要展示的长路径字段。
- 解压与 PNG 编码仍占用 Extension Host 主线程。

### 2.4 数据库整库内存和整库写回

SQLite 当前使用 `sql.js`：

- 打开一个数据库时先 `readFileSync` 读取完整文件。
- `new SQL.Database(buffer)` 会再把数据放入 WASM 内存。
- 分页只减少返回行数，不能减少整库载入内存。

每次新增、修改或删除记录还会：

1. 复制完整数据库到一个新备份。
2. 在内存数据库执行事务。
3. `database.export()` 导出完整数据库。
4. 写临时完整文件。
5. 再复制覆盖原文件。

所以一个单元格回车可能产生数倍数据库大小的内存峰值和磁盘写入。连续编辑时，备份目录也会快速增长。

SQLite 的“全部字段模糊搜索”会对每列执行 `CAST(... AS TEXT) LIKE`，通常无法使用索引，大表搜索仍会全表扫描。

### 2.5 其他可见问题

- `merchant.table`、`mongen.table` 每次改单元格都会重建整个 Webview HTML。
- CSV 编辑器在文档变化时发送完整文件文本。
- 约 10 个面板使用 `retainContextWhenHidden: true`，隐藏后仍保留 DOM 和脚本状态。
- M2 守护进程当前在扩展激活时启动，而不是首次需要重载时启动。

## 3. 第一阶段：快速降载

预计工作量：1-3 天。风险低，建议最先实现。

### 3.1 缩小激活范围

- 删除 `onLanguage:plaintext`。
- 保留 `onLanguage:gomscript`、各个 View、Custom Editor。
- 为兼容 VS Code 1.68，给公开命令补充明确的 `onCommand:boo.*` 激活事件。
- 只有识别为服务端脚本目录的 `.txt` 才启用语言服务。

### 3.2 取消启动时全量审查

- 启动时只诊断当前打开的脚本。
- `boo.diagnoseAll` 保留为用户主动执行。
- HUMAN/GUILD 声明改成按打开文件和文件变更增量维护。
- 首次全工作区索引放到空闲队列，可取消，并严格遵守 `boo.enableDiagnostics`。
- 工作区没有 `Mir200\Envir` 时不启动任何脚本扫描。

### 3.3 延迟自动补丁缓存

保持“路径和密码存在时自动缓存”的产品行为，但改为：

- 激活时只读保存状态和缓存清单头，不解压 PAK。
- 补丁侧栏首次可见，或 VS Code 空闲 5-10 秒后再开始自动补齐。
- 用户开始输入、打开数据库或关闭窗口时允许暂停。
- 自动任务显示可取消进度，已完成包继续复用。

### 3.4 M2 守护进程按需启动

- 注册保存监听和命令时不启动进程。
- 首次保存 `Envir` 脚本且自动重载开启，或首次点击重载/扫描时再启动。
- 空闲一段时间后可退出，下次操作自动恢复。

### 3.5 限制消息刷新

- PAK 进度最多每 100 毫秒或百分比变化时发送一次。
- 相同进度和相同文本不重复发送。
- 侧栏只更新变化的行，不重复发送整个状态列表。

## 4. 第二阶段：数据库根治

预计工作量：4-7 天。收益最高，需要真实数据库回归。

### 4.1 增加原生 SQLite Sidecar

推荐新增一个小型 `BooDatabaseHost.exe`，使用 SQLite C API 和 JSON Lines 协议：

- `catalog`
- `page`
- `search`
- `insert`
- `update`
- `delete`
- `schema`
- `close`

扩展只接收当前页数据，不再把完整数据库载入 Node 和 WASM。所有 SQL 使用预编译参数，不拼接用户值。

选择独立进程而不是 Node 原生模块的原因：

- 兼容当前最低 VS Code 1.68 的 Electron/Node ABI。
- 与现有 M2Reloader、PakBridge 的部署方式一致。
- 数据库崩溃或大查询不会卡死 Extension Host。
- 可以保持 `sql.js` 为兼容回退，逐步迁移。

### 4.2 调整保存与备份

- 打开数据库后的第一次写入创建一份会话基线备份。
- 连续单元格修改直接使用 SQLite 事务，不导出整库。
- 300-500 毫秒内的连续编辑合并为一个事务。
- 结构修改前单独创建完整备份。
- 备份按“最近 N 份 + 最近 N 天”轮转，提供手动保留。

这样仍能安全回退，但不会每按一次回车复制完整数据库。

### 4.3 搜索优化

- 默认优先 `Name`、`Idx` 等常用字段，不默认扫描全部 100 多列。
- “全部字段”作为明确选项，并在大表上分批执行。
- 精确匹配优先使用索引。
- 查询被新请求替代时调用 SQLite 中断，而不只是忽略旧结果。
- 目录、字段和行数按文件 `mtime + size` 缓存，数据库未变化时不重复读取。

### 4.4 MDB

MDB 保持只读。读取和搜索放入 Worker 或 Sidecar，按 500 行分块并允许中断；面板隐藏时释放 Buffer 引用，主动触发资源清理。

## 5. 第三阶段：PAK 与 Webview

预计工作量：3-6 天。保持全量解压，不改变素材序号和空白图片。

### 5.1 PAK Worker

- 将解压、调色板转换、PNG 编码和写盘移动到 Worker Thread 或独立 Helper。
- Extension Host 只处理任务队列、取消和结果清单。
- 继续按 PAK 顺序逐包处理，避免并发大包造成内存峰值。
- 每处理固定数量图片主动释放中间 RGBA Buffer。

### 5.2 缩小素材消息

发送到 Webview 的素材只保留：

- `id`
- `name`
- `url`
- `pakName`
- `willIdx`
- `localIdx`
- `width`、`height`
- `offsetX`、`offsetY`

不发送磁盘绝对路径、PAK 绝对路径等界面不需要的重复字段。素材按 PAK 或 500-1000 条分块发送，Webview 分帧合并。

### 5.3 完成所有素材弹窗虚拟化

主素材列表已经虚拟化，按钮选择器和特效选择器仍使用 `folderAssets.forEach` 生成全部图片。两处改用与主列表相同的虚拟网格，并复用搜索索引。

### 5.4 缓存索引

- `EffectImageList.txt` 以 `mtime + size` 缓存，每次操作仍检查是否变化。
- PAK manifest 解析结果按文件指纹缓存。
- 关闭一个 PAK 时只移除该包数据，不重建其他包 URL。
- 重新读取时只重解码已变化或用户指定的 PAK。

## 6. 第四阶段：语言服务和编辑器

预计工作量：3-5 天。

### 6.1 补全索引

- 启动时按引擎建立 `Map<命令名, 文档>`。
- 建立按首字母或前缀分桶的候选索引。
- 悬停改为 O(1) Map 查询。
- 命令数据或引擎切换时才重建索引。

### 6.2 增量文档分析

- 块上下文只重算变更行之后的区域。
- 使用 `DocumentSemanticTokensProvider` 的增量或 Range 方式。
- 大文件仅分析可见区和变更区，后台空闲时补全索引。
- 诊断防抖按文档分别管理，避免一个文件输入取消另一个文件的诊断。

### 6.3 表格和 CSV

- 表格单元格保存后只更新该行，不重新设置整个 `webview.html`。
- 外部文本变化时发送行级 diff。
- CSV 保存和刷新使用分块或版本号，避免每次发送完整文本。

### 6.4 面板生命周期

仅 UI 编辑器、地图标识编辑等确实需要保持现场的页面使用 `retainContextWhenHidden`。颜色表、统计、帮助、扫描结果等页面隐藏后允许释放，并在再次显示时重建。

## 7. 验收指标

建议加入本地性能日志，不上传用户数据。记录阶段耗时、文件数、数据库大小、PAK 图片数、Extension Host 内存增量。

| 场景 | 目标 |
| --- | --- |
| 普通文本打开 | 不激活 BOO，额外耗时接近 0 |
| 打开服务端工作区 | 首屏不执行全量脚本扫描和 PAK 解压 |
| 扩展空闲 | BOO 额外 CPU 接近 0 |
| M2 未使用 | 不存在 M2Reloader 常驻进程 |
| PAK 进度消息 | 不超过每秒 10 次 |
| 20,000 素材主列表 | DOM 只保留可见行，滚动无持续增长 |
| 素材选择弹窗 | 不一次创建 20,000 个图片节点 |
| 100 MiB SQLite 首屏 | 不在 Extension Host/WASM 中复制整库 |
| 单元格修改 | 不复制、导出和重写完整数据库 |
| 连续编辑 | 合并事务，界面输入不被磁盘备份阻塞 |

测试至少覆盖：

- 4 核、8 GiB 内存、机械硬盘或低速 SATA SSD。
- 10,000 行以上脚本目录。
- 100 MiB 以上 SQLite。
- 20,000 张以上素材缓存。
- M2 开启和未开启两种状态。

## 8. 推荐实施顺序

1. 缩小激活范围，取消启动全量审查。
2. PAK 自动缓存延迟到空闲或侧栏可见。
3. M2Reloader 按需启动，PAK 进度节流。
4. 数据库改用原生 Sidecar 和会话级备份。
5. 虚拟化素材选择弹窗，缩小素材消息。
6. 补全索引和增量文档分析。
7. 表格、CSV 和非必要 Webview 生命周期优化。

前三项改动小、用户体感最明显；数据库 Sidecar 是解决“大数据库低配置不可操作”的关键项；PAK Worker 和语言服务增量化用于消除后续高峰卡顿。
