# PAK 密码文件格式诊断报告

- 检查日期：2026-08-07
- 检查版本：V4.3.0
- 检查范围：`Pak.txt` / `JpkList.txt` 的读取、路径匹配、密码优先级以及 PAK/JPK 解析调用链
- 安全边界：报告不记录、不展示任何真实密码

## 一、结论

当前扩展实际接受以下两种写法：

```text
PAK路径|密码
PAK路径|密码|0
```

这两种写法在现有实现中的密码解析结果相同，**缺少第三列本身不会导致密码失效**。本机两列 JPK 密码表和三列 `|0` PAK 密码表均已通过脱敏匹配验证。

真正存在风险的是：

1. `PAK路径|密码|1` 的第三列会被读取为 `option`，但随后被完全丢弃，未传入任何 PAK 解析器。
2. 补丁管理中已保存的旧密码优先于当前密码文件，用户改过 `Pak.txt` 后仍可能继续使用旧密码。
3. 二次加密、普通密码错误和部分解析失败目前可能被归到同一类“密码错误”，提示不够准确。

因此，用户反馈的“有第三列/没有第三列导致密码失效”，更准确的解释是：

- 两列与 `|0`：当前兼容，格式差异不是根因。
- `|1`：代表另一种加密语义，但当前扩展没有执行该语义，是首要缺口。
- 改过密码后仍失败：还可能是安全存储里的旧密码覆盖了密码文件。

## 二、格式语义

| 格式 | 现有读取 | 当前实际行为 | 结论 |
|---|---:|---|---|
| `路径|密码` | 支持 | 密码正常参与匹配；加密模式为“未声明” | 应继续兼容，尤其是 JPK 密码表 |
| `路径|密码|0` | 支持 | 第三列被保存，但解析时与两列完全相同 | 普通 PAK 的兼容格式 |
| `路径|密码|1` | 表面支持 | 能读到密码和 `1`，但 `1` 未进入解析流程 | 当前不具备完整支持 |
| 少于两列 | 不支持 | 整行跳过 | 合理 |
| 多于三列 | 宽松接受 | 第四列以后被静默忽略 | 建议改为格式警告 |

本地引擎帮助明确记录了 PAK 二次加密功能；第三方工具说明进一步把 `|1` 解释为二次加密补丁，把 `|0` 解释为普通导入格式。第三方说明只能作为旁证，不能替代真实 `|1` 样本的运行验证：

- 整理前本地帮助副本（已外部归档，不进入源码仓库）：`docs/engine-reference/md/01-引擎更新日志.md` 中记录了 Pak 二次加密相关能力。
- 外部旁证：[PAK 批量转换工具说明](https://www.7bbz.com/tool/bbei/10587.html) 明确区分 `|0` 与 `|1`。

## 三、当前代码调用链

### 1. 密码表读取

`src/utils/pak-password.ts` 当前按 `|` 拆分：

- 第一列写入 `configuredPath`。
- 第二列写入 `password`。
- 第三列写入可选的 `option`。
- 两列和三列都会生成有效记录。

问题在于，后续 `resolvePakPasswordFromRecords` 只返回一个密码字符串，不返回原记录，因此 `option` 在这里永久丢失。

### 2. PAK/JPK 解析

`src/utils/archive-index.ts` 和 `src/utils/pak-reader.ts` 的公开参数都只有 `password`，没有普通加密、二次加密或自动识别模式。解析器只能根据文件头选择 GEEPAK2、GEEPAK3、GAMEOFMIR、GAMEOFMIR2 或 JPK 分支，无法根据密码表第三列切换二次加密流程。

### 3. 密码优先级

UI 编辑器当前优先使用密码文件，找不到后才使用已保存密码，顺序合理。

补丁管理当前顺序为：

```text
本次手动输入 > 已保存密码 > 密码文件
```

这会造成一个可复现的失败条件：用户先手动保存过密码，后来修改或更换 `Pak.txt`，补丁管理仍使用旧密码。解析失败后也不会自动使用密码文件中的新值重试。

## 四、脱敏样本验证

### 1. 三列 `|0` PAK 样本

- 密码记录：1555 条
- 第三列：1555 条全部为 `0`
- Data 目录内 PAK：857 个
- 成功匹配密码：774 个
- 未匹配：83 个
- 未匹配原因：83 个文件名在密码表中都不存在，不是路径重定位或第三列造成的失败

### 2. 两列 JPK 样本

Data：

- 密码记录：146 条
- 第三列：全部缺省
- JPK 文件：19 个
- 成功匹配：19 个

Graphics：

- JPK 文件：160 个
- 成功匹配：130 个
- 未匹配：30 个
- 未匹配原因：30 个文件名均未出现在密码表中

### 3. 格式矩阵

使用临时假密码分别构造两列、`|0` 和 `|1` 三行后，三行都能被当前读取器解析并返回密码。该结果同时证明了缺陷：`|1` 虽然被读到，却没有改变后续行为。

### 4. 编码

本机已检查的真实密码表均为 GBK，可被当前实现读取。当前代码固定优先按 GBK 解码；如果将来用户提供无 BOM 的 UTF-8 文件且路径或密码含非 ASCII 字符，可能出现无替换字符的乱码，属于潜在兼容风险。

## 五、根因优先级

### P0：第三列语义丢失

`option` 只存在于密码记录对象，路径匹配返回值却退化成单一字符串。`|1` 最终与 `|0` 走同一解析路径。

可能表现：

- 正确密码仍提示密码错误。
- 普通解析器报索引异常、解压异常或派生密钥失败。
- 用户反复重新输入同一正确密码仍无法打开。

### P1：旧保存密码覆盖当前密码表

补丁管理先读 VS Code SecretStorage，再读密码表。只要旧值存在，新的密码表值就不会被尝试。

可能表现：

- 同一个 PAK 在 UI 编辑器能打开，在补丁管理中失败。
- 删除扩展数据或换工作区后突然恢复。
- 修改 `Pak.txt` 后错误仍保持不变。

### P1：错误分类过宽

当前主要依赖错误文本中是否含“密码错误”判断。二次加密不支持、派生密钥失败和真实密码错误可能混在一起，用户无法判断应该改密码还是改格式。

### P2：文本编码兼容

GBK 样本无问题，但 UTF-8 无 BOM 且含中文路径或中文密码时存在误解码风险。

### P2：同名文件歧义

当密码表中存在多个同名 PAK/JPK，并且同一匹配优先级对应不同密码时，当前实现会返回“未找到可用密码”。这是保护性行为，但提示没有说明是同名冲突。

### P3：分隔符限制

当前没有转义规则，密码本身不能包含 `|`；第四列以后会被静默忽略。这不是已发现样本的主要原因，但应在格式校验中明确提示。

## 六、建议的兼容修复方案

本报告阶段不修改解析行为。后续实施时建议按以下顺序：

1. 将密码解析结果由 `string` 改成结构化结果：路径、密码、模式、来源文件和匹配级别一起返回。
2. 将第三列规范为 `normal(0)`、`secondary(1)`、`unspecified(缺省)`，拒绝未知值并给出行号。
3. 保留两列格式：JPK 继续按现有方式处理；旧 PAK 两列先按普通模式兼容，不能静默假装支持二次加密。
4. 在所有 PAK 调用层传递加密模式。`|1` 在真正实现并验证二次加密解析前，应明确提示“二次加密 PAK 暂未支持”，不要提示用户密码错误。
5. 调整补丁管理优先级为：本次明确输入 > 当前密码文件 > 已保存密码。文件密码失败时，清除旧保存值并允许一次明确重试。
6. 使用已有的 `decodeTextFile` 自动识别 UTF-8 BOM、严格 UTF-8 和 GBK。
7. 错误提示中显示匹配来源、配置行、模式和路径匹配方式，但绝不显示密码。
8. 增加两列、`|0`、`|1`、GBK、UTF-8、同名冲突、密码更新和手动密码回退的自动化测试。

## 七、验证边界

本次已经确认代码会丢弃第三列语义，也确认了两列与 `|0` 的现有兼容性。当前本机样本中没有找到合法、已知正确密码且第三列为 `|1` 的 PAK，因此尚不能声称已经掌握二次加密算法，也不能仅凭更新日志猜测实现。

正式支持 `|1` 前至少需要：

1. 一个用户有权提供的 `|1` PAK。
2. 对应的正确密码和官方/参考工具成功结果。
3. 文件结构、索引数量和至少若干图片像素的对照验证。
4. 普通 `|0`、两列 PAK 和两列 JPK 的完整回归。
