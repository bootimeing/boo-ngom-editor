日期：2026-09-23。类型：验收参考。输入目录：标准 PAK 样本目录。

## 结论

目录内共 5 个 PAK，当前 BOO 生产读取链路兼容其中 2 个，另 3 个因未实现对应格式而被拒绝。当前工作区编译运行代码与上一轮独立 V4.3.5 JPK 修复候选包的结果一致。

本轮是只读分析，不是兼容修复或自动转换发布。所有源文件 SHA-256 前后相同。统一密码只经 stdin 进入本地验证进程，报告与诊断脚本不保存密码。

## 已完成的验证

对每一个文件都实际调用当前插件的两个生产入口：

- `openArchiveIndexed`：高速索引模式。
- `decodePakFully`：兼容 PNG 缓存模式。

PAK 桥使用对应运行目录中实际捆绑的 `boo-pak-bridge.exe`，独立临时端口、隐藏进程、独立临时缓存；不借用或停止用户现有的桥接服务。验证结束后只关闭本轮启动的进程，并清理本轮临时缓存。

对 GOM.pak 和 gee-V8-翎风.pak 各自的全部 1,200 槽（包括空槽）执行：

1. 通过高速索引逐槽解码 PNG。
2. 检查 PNG 签名、宽高、IDAT 解压长度。
3. 对照兼容缓存的槽号、空槽状态、宽高和 X/Y。
4. 对照高速与兼容模式的 PNG 完整字节。
5. 用实际 `ArchiveImageWorkerPool` 再读取每一槽，要求与同步生产读取结果逐字节相同。
6. 重开高速缓存，确认命中缓存。
7. 比较原文件读取前后的 SHA-256。

结果：每个运行目录完成 2,400 个槽位校验，覆盖 1,664 张真实图片和 736 个空槽；零逐帧错误，零被跳过素材，零校验恢复。源码运行目录与包内运行目录的逐文件计数、状态及 PNG 集合摘要全部一致。

这验证了实际读取、像素输出和 Worker 路径；没有启动原版 GM 工具箱或游戏客户端进行全图对照，也没有进行 VS Code 原生鼠标操作验收。正常输出的首图已保存并查看，其余以逐槽机器校验为证。

## 三个未兼容文件的原因

### HXM2：已有源码参考，现在也有真实样本

当前 BOO 的 `src/utils/pak-reader.ts` 格式探测只接受 GEEPAK2、GEEPAK3、GAMEOFMIR、GAMEOFMIR2；HXM2 落入 UNKNOWN，高速和兼容模式均拒绝。失败发生在密码验证和内部索引读取之前，不能报告为已经确认的密码错误或图片损坏。

本机 GXX 的 `GxxSource/GameOfGeeM2/Client-HGE/ReadResources/Pak.pas` 存在对应读取实现：

- 67 行：5 字节 Lz 文件标识结构。
- 836 行：HXM2 格式识别。
- 855 行起：解密后由 `bfType` 区分 V0/V1；不能只凭 HXM2 签名判断具体版本。
- 1214 行：LzPak 全局头解密函数。
- 1403 行起：索引读取；V0 每项包含地址与长度，V1 每项为地址，不能直接复用 GEE 索引结构。

判断：可优先进入独立 profile 的兼容实现与差分验证。此前“缺真实 HXM2 样本”的条件已解除，但本轮尚未解开它的索引，也未验明其 V0/V1 或像素分支。不能把“有源码+有样本”提前写成已支持。

### 两个 PACK4.0：缺少对应的生产解析器

两者开头均为 `PACK4.0 `。当前 BOO 没有这个格式的探测、密码处理、索引和像素解码分支。限定搜索本机 GXX、BOO、资源工具参考源码后，没有找到可直接复用的 PACK4.0 完整读取器；另一个本地项目报告也将 PACK4.0 记录为未识别格式。

判断：需要单独研究真实头布局、密码验证、索引、压缩和图片记录，再分别验证这两个样本。当前不是“已证明无法实现”，也不是“只加一条后缀/签名判断即可支持”。本轮未验证所给密码对其内部加密是否有效，未判定数据是否完整。

## 与自动规范化方案的关系

这批样本揭示两类问题必须分开：

- 已知格式的布局/索引残留问题：在能够确定原始槽位和图片内容时，可直接兼容或生成规范化副本。
- 整个格式家族尚未支持：必须先实现可靠 reader；当前转换器也不能凭空取得原始图片 ID 和像素。

因此，本批 HXM2 与 PACK4.0 的优先事项是新增格式读取，不是将它们强行标为 GEE/GOM 后重新保存。GEE/GOM 两个已通过文件无需自动转换。
