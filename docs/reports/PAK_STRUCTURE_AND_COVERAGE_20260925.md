# PAK 结构与当前兼容覆盖核查

日期：2026-09-25。对象：BOO 扩展 V4.3.6，以及本机 GXX 的特定版本源码。

> 后续更新：本报告保留调查时状态。可追溯规范、只读检查器和HXM版本字段校准见 [前置实施](PAK_STRUCTURE_IMPLEMENTATION_20260925.md)。生产 GOM/GEE3 重叠、有界解压及已知坏槽状态随后已修，见 [读取链路修复](PAK_READ_INTEGRITY_20260925.md)；其他历史布局和完整状态 UI 仍不能据此视为已完成。

本文是结构与证据参考，不是“所有 PAK 已兼容”的声明。实施顺序见 [完整展示实施与验收方案](PAK_COMPLETE_DISPLAY_PLAN_20260925.md)。本轮没有修改生产解析代码、源素材、用户缓存或安装环境，没有再次打包。

## 1. 当前结论

- 对于**格式版本已经实现、密码正确、数据完整**的素材包，完整读取图片及其固有元数据是可实现的。
- 密码不说明文件采用哪种结构，也不能恢复已经丢失的数据。PAK 是扩展名，不是单一格式。
- V4.3.6 对桌面五个标准样本的 6000 个逻辑槽位，本轮重新验证通过；这不等于所有历史变体、所有色深或客户端渲染模式已验收。
- 本轮合成实验确认：损坏槽位与空槽状态混淆、GOM 相邻块重叠未拦截、通用图片解压缺少前置输出大小限制。还确认两项需要真实样本验证的结构边界。

## 2. “所有数据”有三个不同范围

| 范围 | 包内是否通常具备 | 当前核查结论 |
| --- | --- | --- |
| 逻辑图片序号、空槽、宽高、X/Y、像素、透明度 | 已实现的图片归档分支具备相应字段或规则 | 是完整读取的主要验收对象 |
| 全局版本、色深、压缩、文件偏移、保留字段、未知区段 | 取决于具体分支 | 读取器没有完整对外展示全部原始字段；未知字段不能臆测含义 |
| 物品名称、数据库 IDX→Looks、动作分组、速度、方向、发光混合、脚本坐标 | 不保证存在于图片包内 | 需要数据库、脚本、资源映射或特定客户端规则，不能仅靠密码推导 |

一个能正确输出 PNG 的读取器，不等于完整文件结构查看器，也不等于游戏客户端。

## 3. 总体构造

下面是逻辑层次，不表示所有格式都按这个物理顺序存储。PACK4 的索引位于尾部。

```text
文件签名 / 全局头
  ├─ 格式家族、版本、槽位数量、索引位置等
  └─ 密码校验 / 解密参数（具体范围因格式而异）
             ↓
逻辑索引表：图片 ID → 文件中的图片记录位置
  ├─ 零偏移：该 profile 定义的空槽，保留原 ID
  └─ 非空项 → 图片头：宽高、X/Y、像素类型、透明标志、负载长度
                         ↓
                  原始或压缩像素负载
                         ↓
                  可选独立透明度平面
                         ↓
                  按该 profile 规则转 RGBA
```

物理顺序与逻辑编号可以不同。不能通过扫描找到的图片顺序重新编号；动画与脚本引用的是原逻辑 ID。透明 PNG 也不能一律当成空槽：一张有记录但全部透明的有效图片仍然有自身尺寸、偏移和状态。

## 4. 已实现分支的物理布局

以下仅描述当前代码明确接受的结构，不是对同名引擎所有版本的通用规范。偏移从零开始，未特别说明的整数均为小端序。

| 分支 | 全局区域 | 索引 | 图片头 | 像素主要约定 |
| --- | --- | --- | --- | --- |
| GAMEOFMIR | 10 字节签名区 + 256 字节头，共 266 字节 | 当前接受的 profile 为头后 `槽位数 × 4` 字节偏移表 | 16 字节 | 支持的布局使用 DIB 行序；GOM 透明色规则独立处理 |
| GAMEOFMIR2 | 13 字节签名区 + 256 字节头，共 269 字节 | 当前接受的 profile 为头后 `槽位数 × 4` | 16 字节 | 同上，不能只凭 `.pak` 判断 |
| GEEPAK2 | 常规签名区 + 256 字节头，总头区域 266 字节 | 当前路径要求索引起点 266，4 字节偏移项 | 16 字节 | 密码/头变换不是普通 DES-CBC；具体掩码由离线引擎提供 |
| GEEPAK3 | 常规全局区域 266 字节；接受部分声明 headerSize=269 的变体 | 当前验证的 indexOffset=266，4 字节偏移项 | 16 字节 | main、legacy、alternate-global 分支；索引与图头有不同周期变换 |
| HXM2 / Lz V1 | 5 字节 `HXM2.` + 256 字节头 + 1 字节，共 262 字节 | 当前接受 indexOffset=262，4 字节偏移项 | 16 字节 | 底向上行序；独立 alpha 平面与内嵌 alpha 不能混用 |
| PACK4.0 标准分支 | 64 字节 | 尾部压缩索引；解压后为 40 字节不透明前缀 + `槽位数 × 4` | 23 字节 | 当前支持 type=3、未压缩、顶向下 BGRA32 |
| PACK4.0 KSF 分支 | 64 字节，槽位数字段与标准分支不同 | 尾部索引先 XOR 再解压 | 23 字节，其中前 16 字节 XOR | 当前支持 type=3；像素前最多 128 字节 XOR，余下像素不按此规则加密 |

### 4.1 常见 16 字节图片头

GOM/GEE/HXM V1 的图片头在解密后的字段位置类似，但同一个 type/flags 组合的像素语义不保证跨家族相同。

| 相对偏移 | 长度 | 当前使用的含义 |
| --- | ---: | --- |
| 0 | 1 | 像素类型 |
| 1、2 | 各 1 | 保留或 profile 专用字段，未通用解释 |
| 3 | 1 | alpha/布局标志 |
| 4 | 2 | 宽度 |
| 6 | 2 | 高度 |
| 8 | 2 | 带符号 X 偏移 |
| 10 | 2 | 带符号 Y 偏移 |
| 12 | 4 | 压缩负载长度；当前这些路径按 0 表示原始布局 |

### 4.2 HXM2 V1 全局头

以下位置相对于解密后的 256 字节头，而非文件起点。

| 相对偏移 | GXX 声明 | BOO 当前使用 |
| --- | --- | --- |
| 42 | Size，4 字节 | 必须为 262 |
| 46 | ImageCount，4 字节 | 槽位数，上限 1,000,000 |
| 50 | bfType，1 字节 | 当前按 UInt32 读取，连同后三个保留字节一起判断 |
| 51–53 | 三个保留字节 | 当前实际要求为零，否则可能误报其他版本 |
| 54 | IndexOffset，4 字节 | 必须为 262 |
| 58 | BitCount，2 字节 | V1 单图布局主要由图片头决定；不是所有全局字段都已暴露 |
| 60 | CreateDate | 当前未作为预览元数据展示 |
| 68 起 | CheckCode 短字符串及相邻保留区 | 用于受支持的校验；敏感派生材料不导出 |

GXX `TPakFileHeader` 还声明 Reserve、KeyData、Chain 等字段；它们不应直接进入用户诊断日志。源码结构参考见文末。

### 4.3 PACK4.0 已验证字段

- 全局头偏移 48：标准分支槽位数；偏移 24：当前 KSF 分支槽位数。
- 全局头偏移 44：尾部压缩索引长度。当前接受的 profile 依据 `文件长度 - 索引长度` 定位索引。
- 全局头偏移 40：存在 profile 特定混淆；本轮没有把它声明为已完整还原的通用索引定位算法。
- 索引解压结果开头 40 字节不是十个图片 ID，不能加入图片数量。
- 图片头偏移 0/2：宽高，需要右移 4 位；4/6：带符号 X/Y；12：type；13：负载长度。
- 当前对 type 非 3、负载长度不等于 `宽 × 高 × 4` 的布局明确拒绝，没有猜测性解码。

## 5. 密码处理与像素转换

### 5.1 密码作用范围

- GOM/HXM 使用 CP936 编码的密码派生材料及特定反馈/头变换；不能以 UTF-8 编码、trim 后的文本或普通 DES-CBC 随意替代。
- GEE2/GEE3 的密码相关变换、固定变换和不同家族掩码必须分别处理。GEE3 的索引变换有 64 项周期，图头有 64 个头的周期。
- PACK4 标准样本的索引和像素不使用密码；“能打开”不代表验证了用户输入的密码。
- PACK4 KSF 是特定区段的重复 XOR，不是整个文件统一 XOR。
- 某些格式没有独立、强认证的密码校验码，只能依靠多个结构不变量确认。此时错误应是“密码或 profile 不匹配”，不能肯定归咎于密码。

### 5.2 当前像素布局

| 分支 | 当前实现的布局 | 尚未覆盖或未完整验收 |
| --- | --- | --- |
| 公共 GEE/GOM 转换 | type/flags：3:0 调色板8位；5:0 RGB565；6:0 BGR24；6:1 BGR24+独立 A8；7:0 BGRX32；7:1 BGRA32 | 其他 type/flags 组合没有通用支持；GEE legacy X/Y 为零的依据需非零偏移实样核对 |
| HXM V1 | type 3/5/6/7，flags 0/1；支持对齐的独立 alpha 平面；raw/zlib | pf15bit、特殊 SD 4-bit alpha 未实现；真实样本只覆盖未压缩 BGR24/no-alpha |
| PACK4 两个已验证分支 | type 3，原始 BGRA32、顶向下 | 其他图片压缩/type、不同索引布局未实现 |

行对齐、上下翻转、BGR→RGB、调色板、色键透明和 alpha 都会影响结果。HXM 32 位独立 alpha 不等同于 GEE 7:1 的内嵌 alpha。GOM/HXM 某些无 alpha 布局的黑色透明规则也不能直接套给全部 GEE。

## 6. 当前读取与展示链

```text
补丁管理 / UI 编辑器打开归档
  → detectPakFileFormat + 对应 reader
  → direct 索引缓存（默认按需）或 legacy 全量 PNG 缓存
  → ArchiveResourceProvider
  → Worker 单图解码（Worker 不可用时可兼容回退）
  → PNG
  → UI 编辑器 / Ctrl+F12 / 地图等消费者
```

现有 Worker、LRU、并发请求合并、虚拟素材列表已经存在，不需要为实现完整展示重新发明这些组件。

direct 缓存保存大类 format、源文件信息、槽位总数、块数、异常总数等。`blocks.idx` 为 24 字节文件头加每块 40 字节记录，包含 ID、负载位置/长度、布局、尺寸与偏移，但没有独立保留细分 profile/family 和每槽错误原因。KSF 另存每张图解码后的短像素前缀，并验证前缀摘要。

`ArchiveResourceProvider` 不会把所有解码异常主动改成透明图；它对明确的 Worker 解码错误仍会抛出。问题之一发生在更早的索引阶段：缺少块记录的槽位，已被统一视作空槽。

### 展示层静态核查

- `media/editor.html` 的虚拟素材格显示缩略图与名称；当前没有逐槽显示“待验证/正常/空槽/不支持/损坏”的状态，也没有在该列表展示压缩、色深、文件位置等完整元数据。
- 列表计数按 assets 长度显示“张图片”，包含保留的空槽，不等于非空图片数。
- 通用 UI 编辑器 `addToCanvas` 初始使用 x=0/y=0 和 PNG 尺寸，没有在此入口应用归档 X/Y。这证明它是排版入口，不是原始坐标查看器；不能据此断言其所有脚本标签都应该统一加偏移。
- Ctrl+F12 渲染器、地图消费者已有多条 offsetX/offsetY 使用路径，不是全局丢失偏移。是否应用偏移还受具体语句/控件和引擎合同影响。
- 本轮未执行 VS Code 原生交互、GM 工具箱 GUI 或游戏客户端逐帧对比，不能将以上静态核查写成最终视觉验收。

## 8. 已复现的问题与研究边界

| 编号 | 结论 | 证据级别 | 用户影响 |
| --- | --- | --- | --- |
| F1 | 少量被容忍的 GOM 坏块只保留异常总数，下游按空槽处理 | 包内运行时合成复现 | 用户无法定位哪些“空图”实际上是读取失败 |
| F2 | GOM 未校验负载与下一图头的重叠 | 包内运行时合成复现 | 能输出 PNG，但部分像素实际上来自下一张图的加密图头 |
| F3 | `inflatePakPayload` 正常路径未按声明长度前置限制解压 | 包内运行时合成复现 | 先分配出大量数据，再由调用方发现长度不符；存在资源消耗风险 |
| F4 | HXM 把版本字节和三个保留字节一起读为 UInt32 | 源码结构 + 包内合成复现 | 非零保留字节可能误报版本；尚无真实非零保留字节样本 |
| F5 | PACK4 按非零 count 判 KSF；零槽加密尾索引会被当标准分支 | 包内合成边界实验 | 空 KSF 可能误判；尚未确认真实工具会生成该空包布局 |
| F6 | GOM 外层包装多个异常为“密码错误，或索引损坏” | 静态确认 | 不支持布局、结构损坏与密码错误不易区分 |
| F7 | direct 的“索引完成”没有覆盖所有图片的负载解码 | 静态确认；按需架构本身合理 | 用户后续访问某图时才发现错误，缺少独立全量验证状态 |
| F8 | HXM V0、pf15bit、特殊4-bit alpha；PACK4其他布局 | 明确的未实现分支 | 有正确密码仍可能不支持，不属于密码修复问题 |
| F9 | GEE legacy 的 X/Y 固定为0，只解密部分图头字段 | 静态确认，正确性未定 | 需要含非零偏移的真实参考判断，不可把猜测作为修复依据 |
| F10 | `GEEM2` 不在当前 PAK 检测与 reader 路由中 | 静态确认 | GXX 提及的历史家族不能直接视作已支持 |

### 实验的精确结果

1. GOM 合成包 1659 槽：ID 1260 的图头尺寸损坏，ID 1655 为真实空槽。两者 isBlank=true、表内 blank=1，最终返回完全相同的 1×1 透明 PNG；异常总数=1，后续 ID 没有移位。
2. GOM 合成包：将第一图声明宽度从 1 改为 2，不改变物理负载和下一索引。读取器接受 4 字节重叠，skipped=0，输出宽2的 PNG。它并未因“输出了图”而满足正确性。
3. 用 1040 字节 zlib 压缩块表示 1 MiB 数据，向 helper 声明期望16字节，helper 仍返回1 MiB。实验规模有界，未执行内存耗尽测试；调用方仍有事后长度检查。
4. HXM bfType=1、首个保留字节=1，被报告为“不支持版本257”。实验没有证明非零保留位在真实写入器中合法，只证明当前字段读取方式。
5. 合成零槽 PACK4 XOR 索引，在正确合成密码下报告“尾部索引损坏或格式不受支持”。缺真实空包合同，不能直接放宽分支判断。

GEE2、HXM、PACK4 的已核查路径包含相邻块重叠检查；GEE3 的两种读取入口主要做文件范围与重复偏移检查。不能因为一个 reader 的校验充分就推定其他 reader 等价。

## 9. 为什么“同格式转换后能打开”不能代替解析规范

GM 同格式重写可能统一头字段、重建索引、改变压缩/像素布局、消除写入器历史差异，也可能略过无法读取的记录。没有同一个问题包的转换前后对照，无法确认是哪种情况。

本轮标准包及合成实验没有提供这种前后配对证据，不能宣称自动重写就能无损修好所有文件。长度匹配的 checksum 容错也不能证明输出像素就是原始像素；应保留“恢复但未独立验证”状态。

真实截断、缺失图片字节、缺少外部动作/数据库语义，不会因为持有密码或转换文件扩展名而恢复。
