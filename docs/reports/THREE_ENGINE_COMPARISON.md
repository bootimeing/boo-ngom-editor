# GOM、翎风与 996PC 引擎差异报告

> 核查日期：2026-07-23  
> 当前扩展版本：V4.2.1  
> 结论用途：补全、悬停、代码审查、数据库、素材与后续引擎接入

## 1. 核查资料

本次使用的原始资料：

- GOM：整理时使用的 GOM 本地帮助副本。
- 翎风：整理时使用的翎风本地帮助副本。
- 996PC：整理时使用的 996PC 本地帮助副本。
- 996PC 服务端：同目录下的 `Mir200`、`表格`、`GameCenter.exe` 等文件
- 当前扩展：`data`、`src`、`tests` 中的语言数据与实现

CHM 已离线展开并建立可检索索引：

| 引擎 | 目录主题 | 有效文档 | 命令形态词 |
| --- | ---: | ---: | ---: |
| 996PC | 871 | 824 | 1737 |
| GOM | 865 | 844 | 1588 |
| 翎风 | 1028 | 846 | 1216 |

“命令形态词”只用于发现候选项，不能直接证明命令兼容。996PC 与 GOM 有
1093 个词重叠，与翎风有 777 个词重叠，三者共同出现 753 个；996PC 另有
620 个候选词未在另外两套索引出现。这说明 996PC 在脚本血统上更接近 GOM，
但仍有很大的独立能力面。

## 2. 总结结论

1. GOM、翎风、996PC 必须视为三套独立语言，不能用“公共命令库 + 少量差异”实现。
2. 同名命令不代表同语法。例如 `SENDMSG` 的颜色参数在 GOM/996PC 中位于消息前，
   在翎风中位于消息后。
3. 996PC 的传统脚本结构接近 GOM/HeroM2，但数据库、资源文件、新 NPC UI、
   自定义职业和跨服配置已经形成独立体系。
4. 996PC 帮助本身存在拼写和参数数目冲突，不能把全文抽取结果直接加入补全。
5. 当前扩展已完成三引擎运行时隔离；996PC 已按自身帮助和真实服务端完成核心语言、JPK、XLS 数据库与 M2 验收。

## 3. 核心差异矩阵

| 能力 | GOM | 翎风 | 996PC |
| --- | --- | --- | --- |
| 脚本基本结构 | `[@标签]`、`#IF/#ACT/#SAY` | 同类结构 | 同类结构，另有 HeroM2 兼容区 |
| 同名命令语法 | GOM 自有参数顺序 | 多条命令与 GOM 不同 | 常接近 GOM，但不是完全相同 |
| 物品/怪物/技能数据 | 传统数据库体系，最新版支持 SQLite | 传统数据库体系，字段语义有差异 | 只读取 `cfg_item.xls`、`cfg_monster.xls`、`cfg_magic.xls` |
| 玩家与账号数据 | 非本报告重点 | 非本报告重点 | `Setup.json` 明确配置 SQL Server |
| 资源主链 | `PAK -> WIL -> WZL` | PAK/WZL 能力需按页面逐项核验 | `JPK -> WZL -> CDN`，转换文档要求 PAK 转 JPK |
| UI 扩展 | WIL/PAK 按钮、NPC 对话框 | 有大量兼容命令与 GEE 控件写法 | 独立组件体系：Text、Img、Button、Layout、ListView、UIModel 等 |
| 自定义职业 | 传统职业扩展 | 各自实现 | 明确支持职业 5-25、独立动作表与 JPK 素材规则 |
| 跨服 | 有跨服相关能力 | 有跨区跨服设置 | 最多 5 服，使用 `cfg_kuafuval.xls` 和独立触发 |
| 红点系统 | 未发现同结构表 | 未发现同结构表 | `cfg_redpoint.xls` 加脚本红点配置 |

## 4. 已确认的同名不同义

### 4.1 `SENDMSG`

- GOM：`SENDMSG 类型 [字体颜色] [背景颜色] 消息`
- 翎风：`SENDMSG 类型 消息 [字体颜色] [背景颜色]`
- 996PC：帮助定义与 GOM 相同，颜色位于消息前；类型 8、9 又有 996PC 自身规则

因此三套数据必须各存一份。即使 GOM 与 996PC 当前写法相同，也不能让
996PC 继承 GOM 条目。

### 4.2 `ADDBUTTON`

- 996PC 旧命令参数 8 只说明是否可移动。
- 当前 GOM 文档的参数 8 为 `是否可移动|按钮分组`。
- 996PC 另有新的组件化 `AddButton` 和 PC/移动端坐标体系。

直接复用 GOM 补全会让 996PC 用户输入不存在或含义错误的分组参数。

### 4.3 `HTTPPOST`

- GOM 页面定义为 3 个参数：地址、格式、内容。
- 996PC 页面标题正文写成 `HTTPPSOT`，格式行称 5 个参数，随后又说明到参数 6，
  示例实际使用 `HTTPPOST`。
- 翎风索引未找到可作为定义证据的对应页面。

这一项必须人工核对运行结果。帮助内部冲突解决前，只能保留为“待验证”，
不能进入正式补全和严格审查。

### 4.4 配置读写与 OK 框

996PC 的版本转换说明明确指出：

- `ReadConfigFileItem` 的接收变量不要包 `<$STR(...)>`，与 GOM 写法不同。
- 放入自定义 OK 框的物品不会再被普通背包检测命令发现，应使用
  `CheckBoxItemCount`。
- 怪物表 `SPEED` 字段实际代表躲避；GOM 有效上限 255，996PC 上限 65535。

这些都是“命令名存在，但参数或运行语义不同”的典型情况。

## 5. 数据库差异

996PC 的“服务端表结构”页面明确说明：

- 表格目录为 `Mir200\Envir\Data`。
- 引擎只读取指定 Excel 表，对应 TXT 和 DB 文件不读取。
- 文件必须保存为 Excel 97-2003 `.xls`。
- `cfg_item.xls` 取代 `StdItems.DB`。
- `cfg_magic.xls` 取代 `Magic.DB`。
- `cfg_monster.xls` 取代 `Monster.DB`。
- `cfg_level.xls` 优先于 `Exps.ini`。

当前部署样例进一步确认：

- `cfg_item.xls` 有 25 列，属性改为
  `职业#属性ID#属性值|...` 的组合字段。
- `cfg_monster.xls` 有 24 列。
- `cfg_magic.xls` 有 37 列，并提供多级技能等级与熟练度字段。
- `cfg_JobAction.xls` 用于职业动作与素材分组。
- `cfg_redpoint.xls` 用于红点条件、按钮路径和 PC/移动端偏移。
- `Setup.json` 的 `M2DB-Config` 使用 SQL Server 1433 端口。

996PC 转换说明还要求物品 IDX 转换后整体从 10000 开始。因此当前针对
GOM/翎风数据库和 `Looks` 的处理逻辑不能直接套到 996PC。

## 6. 素材与 UI 差异

### 6.1 996PC 素材链

996PC 的补丁读取规则：

1. 优先读取 `Resources\Data\名称.Jpk`。
2. 不存在时读取 `Data\名称.wzl`。
3. 本地仍不存在时，可能通过官方 CDN 获取 WZL。

`EffectImageList.txt` 页面说明该列表只支持 WZL、JPK。版本转换页面也明确要求：

- `.WIL` 批量转换为 `.WZL`
- `.PAK` 批量转换为 `.JPK`

因此扩展使用独立 JPK 解析器、引擎隔离缓存和 `JpkList.txt` 密码处理，不让现有 PAK 解析器冒充 996PC 资源支持。WZL 与 CDN 获取不在本次接入范围。

### 6.2 新 NPC UI

996PC 有 25 个独立组件页面，包括：

- `Text`、`Img`、`Button`、`Effect`
- `Layout`、`ListView`、`CheckBox`
- `ItemShow`、`Input`、`LoadingBar`
- `UIModel`、`Slider`、`Frames`、`CostItem`

其通用面板说明承认部分旧写法来自 GEE，但 PC 端参数、组件属性和触发关系已有
996PC 扩展。因此只能复用解析框架，不能复用 GEE 的参数表。

## 7. 变量与脚本能力

三套引擎都存在自定义变量和 `L$` 列表能力，但扩展范围不同：

- 996PC 支持 HUMAN/GLOBAL/GUILD 自定义变量、嵌套变量和 `L$` 数组。
- GOM 最新文档在 `L$` 基础上又增加了跨玩家共享的 `GL$` 全局列表。
- 翎风也有元素变量，但命令集合和细节应以翎风页面为准。
- 996PC 另有 `ReadExcel`，把读取结果写入 `Excel0`、`Excel1` 等全局值。

996PC 包中虽然存在 `Lua5.1.dll` 和 `cjson.dll`，但帮助索引没有 Lua 脚本页面。
DLL 只能证明运行时依赖，不能据此添加 Lua 补全或审查规则。

## 8. 当前扩展已完成的隔离

V4.2.1 当前实现：

- 引擎注册表统一管理标签、函数文件、常量文件和界面顺序。
- GOM、翎风、996PC 的命令、变量、触发器都具有各自完整的引擎变体。
- 即使多个引擎拥有同一命令，也在运行时生成独立定义，不继承其他引擎正文。
- 函数和常量使用独立文件。
- 补全、悬停、语义索引和代码审查都使用当前引擎索引。
- 代码审查只对“已在其他引擎确认、当前引擎不存在”的符号给出警告；
  未知插件命令不会被误报。
- 多级命令 `M.xxx`、`H.xxx` 会按完整名称检查。
- 补全编辑器最上方提供 GOM、翎风、996PC 标签；全局引擎切换会同步当前页签，也可手动查看其他引擎数据。
- 编辑器的函数和常量标签页也由引擎注册表动态生成，后续不再写死两个引擎。

当前独立索引数量：

| 引擎 | 有效命令 | 命令补全 | 变量 | 触发器 | 函数 | 常量 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| GOM | 710 | 374 | 415 | 89 | 56 | 428 |
| 翎风 | 987 | 715 | 256 | 60 | 643 | 414 |
| 996PC | 542 | 540 | 344 | 82 | 542 | 605 |

未核验条目不会进入补全。真实服务端已确认、但帮助尚未给出完整参数的条目只参与
悬停和兼容诊断，不会向用户推荐不完整语法。历史分类仍保留用于审计，但不再作为
运行时共享数据。

## 9. 996PC 接入结果

完整架构、自动识别、全模块同步切换、Excel/JPK 接口、阶段门槛、测试矩阵与回滚
方案见 [`996PC_INTEGRATION_PLAN.md`](../plans/996PC_INTEGRATION_PLAN.md)。本节保留为摘要。

### 第一阶段：语言数据（已完成）

1. 增加 `996PC` 引擎注册项和设置项。
2. 建立独立的命令、变量、触发器、函数、常量与静态语言数据。
3. 以“定义页 + 参数页 + 示例”三者交叉核验，更新日志只能生成候选。
4. 与 GOM 同名的命令也复制为 996PC 自有条目，不建立继承关系。
5. 文档冲突项默认禁用补全，并在审校报告列出。

### 第二阶段：自动识别（已完成）

使用多证据识别 996PC：

- `Mir200\Setup.json` 中存在 `M2DB-Config`
- `Mir200\Envir\Data\cfg_item.xls`
- `cfg_JobAction.xls`、`cfg_redpoint.xls`
- 996PC M2 或控制器的产品信息

只有多项证据同时成立才自动切换，避免把普通 GOM 服务端误判为 996PC。

### 第三阶段：数据库（已完成核心三表）

已建立独立 `996PC Excel Provider`：

- 只读验证 `.xls` 结构和版本行
- 分别解析 `cfg_item`、`cfg_monster`、`cfg_magic`
- 保留未知列和原始单元格类型
- 写回前制作文件级备份
- SQL Server 角色库先保持只读或不接入，避免凭据与锁风险

### 第四阶段：资源（JPK 已完成，WZL/CDN 不在本次范围）

已建立独立 `JPK Provider`，并保持现有 PAK Provider 行为：

- JPK/WZL 定位优先级
- `EffectImageList.txt` 校验
- 空白帧、序号与密码规则
- PC/移动端资源差异
- 完整像素回归和样例包校验

### 第五阶段：回归门槛（已完成）

996PC 上线前必须满足：

- 每个启用补全都有 996PC 自身来源。
- GOM、翎风、996PC 任一数据修改不会改变另外两个索引。
- 同名不同语法命令有独立测试。
- 选择不同引擎后，补全、悬停和审查结果同步切换。
- 未知插件命令不报错，已确认的跨引擎命令才提示。
- Excel 和 JPK 功能均有真实样例回归。

## 10. 风险结论

目前可以安全交付三引擎独立补全、悬停与跨引擎审查，以及 996PC JPK、核心 XLS 数据库、定向 M2 重载、GOM 兼容旧式 UI 代码生成和小地图 JPK 定位。真实 996PC 服务端 1,790 个脚本文件、797,983 行扫描未发现命令或系统符号错配。

996PC 旧式 NPC UI 的参数与 GOM 一致，已用实际生成函数做逐字输出回归；新组件化 UI 仍作为独立后续能力，不会被错误套用旧式序列化。`MiniMap.txt` 编号换算与 GOM 相同，但资源解析严格限制为 `mmap*.jpk`。
