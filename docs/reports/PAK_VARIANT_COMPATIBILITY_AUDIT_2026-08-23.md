# 传奇资源 PAK 变体兼容性审计

审计日期：2026-08-23

## 1. 结论

当前扩展的 PAK 主线实际覆盖：

- GOM `GAMEOFMIR` / 标准 `GAMEOFMIR2`。
- GEE `GEEPAK2` / `GEEPAK3` 已实现的精确索引配置。
- 相邻资源格式：996PC/XUW GameLib JPK、WIL/WIX、WZL/WZX。

公开的传奇资源编辑器把 PAK 进一步分为 GOM、GEE、V8、LEG、龙族、KSF、361、Apple、GOM 二次加密。当前代码没有 V8、LEG、龙族、KSF、361、Apple、GOM 二次加密的独立检测、密钥配置或索引解析分支。

其中已经能用本机真实文件确认的缺口有两个：

1. `PACK4.0 - 361m2`（361 PAK）无法被当前解析器识别。
2. `GAMEOFMIR2` 非标准尾标记 `14 52` / `28 52` 会先被检测成 GOM，随后又因解析器严格要求 `00 00` 而失败。

其余市场分类只能确认“当前没有专用兼容与回归样本”，不能在没有原始样本、正确密码和参考工具结果时推断算法，也不能直接断言它们必然与现有 GOM/GEE 二进制结构不同。

## 2. 公开格式清单

GM 工具箱资源编辑器公开列出的格式如下：

| 容器 | 公开分类 |
|---|---|
| PAK | GOM、GEE、V8、LEG、龙族、KSF、361、Apple、GOM 二次加密 |
| JPK | 996、XUW |
| WIL | 韩服传奇 2、光通传奇 3 |
| WZL | BLUE PNG |
| 其他 | WIS、MIZ、PDB(HGE)、WTL、ROM(GOH)、LIB、ZL、PSK |

来源：<https://viewer.gmgjx.net/index.html>

GOM 的公开旧更新记录明确提到，商业登录器曾增加“读取二次加密 PAK”，并同时提供 PAK 二次加密工具。因此 GOM 二次加密不能当作普通密码错误处理。

来源：<https://www.tayewan.com/thread-2447-1-1.html>

## 3. 当前代码边界

| 当前分支 | 文件识别 | 解析边界 | 审计判断 |
|---|---|---|---|
| GEE2 | `07 + GEEPAK2` | 依赖离线引擎返回精确全局头与索引 | 已实现，不能外推为全部 GEE2 变体 |
| GEE3 | `07 + GEEPAK3` | 当前已验证的 main/legacy 配置 | 已实现，未知密钥表或全局头仍需样本 |
| GOM2 | `0A + GAMEOFMIR2` | 实际解析严格要求尾部 `00 00` | 标准格式可用，非标准尾标记存在确认缺口 |
| GOM1 | `09 + GAMEOFMIR` | 固定签名与对应密钥流程 | 已实现 |
| JPK | 扩展名与 GameLib 结构探测 | 当前 996PC/XUW GameLib 结构 | 已实现；仍需保留 XUW 独立样本回归 |
| WIL/WZL | 配对索引文件 | 已实现的色深、压缩和 PNG 类型 | 不属于 PAK 变体 |

关键代码位置：

- `src/utils/pak-reader.ts`：只返回 `GEE2`、`GEE`、`GOM`、`UNKNOWN`。
- `src/utils/gom-reader.ts`：GOM2 签名固定为 `GAMEOFMIR2 + 00 00`。
- `src/utils/archive-index.ts`：不属于 GEE/GOM/JPK/WIL/WZL 时直接拒绝。
- `src/utils/jpk-reader.ts`：996PC/XUW GameLib JPK 独立解析。

## 4. 本机真实样本结果

本轮扫描了 D 盘及桌面可访问的 PAK。D 盘全量扫描中，绝大多数传奇样本属于 `GEEPAK3` 或标准 `GAMEOFMIR2`；大量 `05 00 00 00...` 文件来自 Chromium/Electron 资源包，与传奇无关。

### 4.1 361 PAK：确认不兼容

样本：本地 `MapEdit\Hum.pak` 测试文件。

- 文件头：`PACK4.0 - 361m2`。
- 当前 `detectPakFormat` 返回 `UNKNOWN`。
- 现有 GOM/GEE/JPK 解析器没有对应分支。

这已经足够确认“识别层不兼容”。是否为实际客户端正在调用的补丁，还需要对应 361 引擎或项目配置证明；不能仅凭它位于 MapEdit 目录就当作生产素材。

### 4.2 GAMEOFMIR2 尾标记：确认存在解析规则冲突

发现 4 个本机样本：

- 2 个尾标记为 `14 52`。
- 2 个尾标记为 `28 52`。
- 文件来自本地 996PC 测试客户端的 `山海经补丁\map` 目录。

当前检测器只比较前 11 字节，会返回 GOM；`parseGomFile` 又比较完整 13 字节，只接受 `00 00`。因此这些文件会出现“格式看似识别成功、进入解析后失败”的现象。

不能直接删除 `00 00` 校验。下一步必须用正确密码和可成功读取的参考编辑器核对：

1. 两个尾字节是否只是版本/标志位。
2. 全局头是否仍从第 13 字节开始。
3. DES/反馈密钥派生是否变化。
4. 索引槽、图块头、压缩流和坐标字段是否与标准 GOM2 相同。

### 4.3 GEE2/GEE3：属于覆盖边界，不是本轮新增失败

当前扩展已接入 GEEPAK2 和已验证的 GEEPAK3 main/legacy 结构，但这些名称并不能证明所有同签名文件都共用同一密钥表、全局头和索引规则。以后遇到“签名相同但精确索引失败”时，应新增配置档并做样本回归，不能退回扫描 zlib 数据冒充完整索引。

## 5. 尚缺样本的 PAK 家族

| 家族 | 当前状态 | 需要的最小证据 |
|---|---|---|
| V8 PAK | 无专用分支，是否复用 GOM/GEE 未证明 | 原始 PAK、密码、V8 版本、参考编辑器首尾序号截图 |
| LEG PAK | 无专用分支 | 原始 PAK、密码、对应登录器/资源编辑器结果 |
| 龙族 PAK | 无专用分支；公开资料表明存在龙族自有转换格式 | 原始 PAK、密码、龙族引擎版本、参考结果 |
| KSF PAK | 无专用分支 | 原始 PAK、密码、引擎与资源调用配置 |
| Apple PAK | 无专用分支 | 原始 PAK、密码、引擎与参考结果 |
| GOM 二次加密 | 标准 GOM 分支没有第二层处理 | 加密前后同源样本、原密码、参考工具结果 |

只有市场分类而没有样本时，最安全的产品表现是“未识别的传奇 PAK，显示签名与诊断信息”，而不是统一提示“密码错误”。

## 6. 相邻资源格式缺口

这些不是 PAK 变体，但市场上的传奇资源编辑器会一并支持，当前 UI 编辑器还没有对应读取器：

- WIS、MIZ、PDB、WTL、ROM、LIB、ZL、PSK。
- WIL 的韩服传奇 2 / 光通传奇 3 差异，也不应只按 `.wil` 扩展名推断完全兼容。
- WZL 的 BLUE PNG 是已知子类型，其他 WZL 图像类型仍应以真实样本回归为准。

这些容器不应塞进 PAK 解析器，应该继续采用独立 reader 和统一的逻辑槽/图片帧接口。

## 7. 明确排除的同名 PAK

互联网和本机上还有大量与传奇无关的 `.pak`：

- Chromium/Electron `resources.pak`、`chrome_100_percent.pak`、语言包。
- Quake/id Tech `PACK` PAK。
- Unreal Engine PAK。
- No Man's Sky、通用 Rust/Go 资产 PAK 等。

它们只是扩展名相同，不应加入传奇补丁管理。建议先结合客户端目录、引擎类型和传奇签名白名单，再进入资源索引；未知文件只提供诊断，不进行通用 PAK 猜测。

## 8. 建议接入顺序

### P0：修复已确认的 GOM2 尾标记分支

1. 将“格式家族识别”和“具体 profile 识别”拆开。
2. 为 `00 00`、`14 52`、`28 52` 建立显式 profile，不做任意尾字节通配。
3. 获得正确密码和参考结果后，逐项比对全局头、索引、首图、中间图、末图、空槽、坐标和 RGBA 哈希。
4. 标准 `00 00` 样本必须全部保持原回归结果。

### P1：361 PAK 只读探测与预览

1. 先解析 `PACK4.0 - 361m2` 全局头和索引，不先做写回。
2. 使用样本内的首个有效图、空槽、末图确认逻辑序号。
3. 验证图片格式、透明色、坐标偏移和压缩算法。
4. 有至少两个独立 361 样本后再宣称兼容。

### P2：建立未知传奇 PAK 诊断器

输出文件大小、前 64 字节、候选签名、尾部结构、索引候选和压缩流统计；错误信息区分：

- 未支持的格式。
- 密码/密钥派生失败。
- 索引损坏或版本不匹配。
- 图块压缩数据损坏。

### P3：按样本接入 V8、LEG、龙族、KSF、Apple、GOM 二次加密

每个家族都必须建立自己的 fixture、密码注入、逻辑槽清单和像素哈希。即使最终证明某家族复用 GOM/GEE，也应保留独立 profile 与引擎标签，避免后续版本变化互相污染。

## 9. 验收门槛

每种新变体至少需要：

1. 两个不同来源的合法样本，或一组加密前后同源样本。
2. 正确密码，但测试报告和仓库不得保存真实密码。
3. 参考编辑器给出的槽位总数、有效图片数和至少 5 个逻辑序号。
4. 首图、中图、末图、空槽、透明图与带偏移图的 RGBA 哈希比对。
5. 错误密码、截断文件、损坏索引和错误扩展名的负向测试。
6. UI 编辑器、补丁管理、数据库素材、地图/NPC/怪物预览共同回归。

在这些门槛完成前，只能表述为“已识别/实验性读取”，不能表述为“完全兼容”。
