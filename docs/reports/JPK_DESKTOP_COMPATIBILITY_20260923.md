## 根因与改动

### 尾部遗留数据

旧版 `jpk-reader.ts` 要求索引尾部不超过 256 字节，且尾部第一个 uint32 等于当前索引偏移。真实文件不满足这一推断：

- Mon4013：有效索引位于 22,207,040，820 项结束于 22,210,320；后面还有 3,364 字节旧索引/遗留记录。当前有效索引中的 656 个图像块全部可解密、解压与绘制。
- Mon4024：有效索引后有 80 字节，开头是零填充，末尾才是索引偏移。

修复按已解密文件头中的 `count` 和 `indexOffset` 读取有效表，尾部保留为不解释的数据，不扩展槽数。有效表必须完整处于文件内；每一个非零表项仍校验块头和图像负载边界。未放宽密码、标题、槽数上限、图像尺寸和解压长度约束。

### 局部缺损

Mon4024 文件内 `[194560, 759745)` 为连续零字节，跨越了多个已被索引引用的图片块：

- 序号 1：压缩负载损坏，zlib 检查失败。
- 序号 2、3、10、11：20 字节图像头全部为零。

读取器记录全零块头的原始序号，允许其余独立块继续建立索引。高速模式在读取序号 1 时仍报告该图片解码失败，其余图片可按需显示；兼容模式将全部 5 个异常位置保留为空位，在 manifest 和既有补丁管理提示中报告跳过数量。后续图片 ID 不移动，不输出损坏图片的伪造像素。

兼容模式缓存版本升级为 `jpk-active-index-v3`。JPK 解压使用已验证的预期原图长度作为输出上限。其他 PAK 的失败处理保持原行为。

## Mon4028 的剩余证据边界

- 文件实际长 5,385,610 字节。
- 用户提供的候选密码能正确解开 `GameLib`、80 字节头和 13,360 槽计数。
- 声明的索引偏移为 415,140,539，索引结束为 415,193,979，均超出实际文件。
- 文件偏移 5,366,045 处有合法的 227×178 图像头，声明负载长 21,259；该图应结束于 5,387,324，实际缺少最后 1,714 字节。
- 在偏移 606,145 之后只读扫描可确认 249 个压缩图像块；这只能证明部分像素还在，不能证明其原始槽号。不得顺序重编号后宣称能够恢复游戏引用。
- 将文件末尾的 53,440 字节按普通索引及同密码 RC4 索引检查，均不成立：分别有 13,345、13,343 个表项越界。
- 用户反馈 GM 工具箱能打开。已查的本地 Python 参考 reader 同样依赖文件头索引且要求索引结束等于 EOF，不能代表用户所指原版 GM 工具箱的容错行为；本轮没有取得原版 GM 工具箱对这份文件的实际图片/序号对照。

本项保持未完成。下一步需要对照 GM 工具箱打开桌面同一份 Mon4028 后的实际可见图片与序号，或取得其另存的完整 JPK 副本，才能实现有证据的索引恢复。
