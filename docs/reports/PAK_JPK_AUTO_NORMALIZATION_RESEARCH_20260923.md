# PAK/JPK 自动兼容与规范化副本：设计研究

日期：2026-09-23。文档类型：设计解释。状态：当前代码核查与 JPK 隔离实验完成，生产自动转换未实施。

后续样本更新（同日）：用户提供了标准 PAK 样本目录中的 HXM2、PACK4.0、GEEPAK3 和 GAMEOFMIR2 真实样本。HXM2 的“缺样本”条件已解除，生产读取仍未实现；PACK4.0 也需要新增独立格式支持。逐文件结果见 [标准 PAK 兼容性核查](STANDARD_PAK_COMPATIBILITY_AUDIT_20260923.md)。下文“缺样本”的描述是研究当时的条件，不代表收到样本后的现状。

## 结论

可以让用户在一部分索引/布局不兼容时不再手动借助 GM 转换。推荐采用“读取器直接兼容优先，必要时自动生成已验证的同分支规范化副本”，副本只供 BOO 读取，原文件始终保留。

不能把“任何报错 → 用现有 writer 再保存一次”作为通用修复：writer 本身先依赖 reader；reader 不认识源文件，就没有可靠的图片序号和像素可供重建。真正缺失的负载、密码或索引也不能由重打包创造出来。

用户当前没有仍不兼容的 GM 转换前后文件对。本研究不阻塞于新样本，但不声称已复现原版 GM 的全部转换行为，不给出未知格式自动修复成功率。

## 为什么同格式转换可能有效

“同扩展名”不等于“内部字节结构相同”。转换器通常重新写出一个自身支持的标准布局：重算文件头、图片地址、长度与索引，移除不再被引用的旧数据，可能重新压缩图像。原包存在历史残留或不同生成器布局时，重新写出的包可能恰好落在 BOO 支持的子集内。

其中，重新压缩还可能修正非标准压缩封装/校验字段；也可能改变像素格式、透明度或者丢弃坏图。因此“能打开”不是无损证明。GM 是否做了这些动作，必须逐份对照转换前后文件才能确认，不能由用户描述推断其具体算法。

PAK 至少要区分 GAMEOFMIR、GAMEOFMIR2、GEEPAK2、GEEPAK3 main/legacy；JPK 也有 GameLib 和有日期标记的 996M2 变体。扩展名不变时，仍须证明目标 profile 没有改变。

## 本轮实际确认的代码现状

- `src/providers/patch-manager.ts:454` 的 `cacheEntry` 先执行 `openArchiveIndexed`；失败且不属于已确认密码错误时，回退到 `decodePakFully`。这只是读取/缓存路径切换，不会重写 PAK/JPK。
- `src/utils/archive-index.ts:176` 与 `src/utils/pak-reader.ts:196` 的 JPK 入口均调用 `parseJpkFile`；相同索引错误会让两条入口一起失败。GEE 也复用相同解析核心；GOM 的本地与桥接路径有所不同，不能笼统说所有格式完全同源。
- 当前 `tools/PakBridge/src/offline_bridge.py:427` 只提供 GEE/GEE2/GOM 头部、索引和 profile 服务，没有转换/规范化接口。此 checkout 没有资源编辑器 worker-client 或 JPK writer，其他项目及历史技能提及的功能不能当作本仓库现有能力。
- 本地独立参考工程的 `paktool/` 有 JPK、GOM、GEE writer，具备原始块复制、重建索引和像素回读校验，可作为实现参考；它不是原版 GM 工具箱源码。
- 这些 writer 的构造函数先调用严格 reader；三个 `save_as` 都拒绝没有待保存编辑的会话。JPK Python reader 目前还要求有效索引结束恰为 EOF。因此不能不经适配直接拿来做失败自动重建。
- 当前 `archive-index.ts` 把 `pakPath` 同时用于资源身份、源文件变化检查和底层图片读取。增加副本必须拆开“原包身份”和“实际读取路径”，否则会失去原包更新检测或读错文件。
- `src/utils/gom-reader.ts` 当前会拒绝重复块偏移以及不等于头大小的索引起点。这是需要真实样本研究的边界，不代表可直接放开：合法共享块引用、未知 profile 和损坏数据必须区分。

## 隔离实验：标准化结构是否真的有帮助

实验只在临时目录生成候选文件，结束后清理临时副本，没有修改桌面原包，也没有改生产解析器。密码仅由 stdin 输入，没有保存到脚本或报告。

`Mon4013.jpk` 原包为 22,213,684 字节，820 槽，656 张图和 164 个空槽，有效索引后还有 3,364 字节残留数据。

实验保留每张图的完整原始加密记录，按原逻辑 ID 写出记录和新索引，仅更新全局头的索引地址，不重新编码像素。结果为 22,210,320 字节：

- 严格独立 Python reader 读取原包：失败，要求索引结束等于 EOF。
- 同一严格 reader 读取候选：通过，820 槽、656 张图。
- BOO 当前 reader 重开候选：通过。
- 656 张图片的完整记录字节、RGBA、宽高、X/Y、位深、Alpha、压缩属性逐项相同。
- 全部图片逻辑 ID 与空槽保持一致，全局头除索引地址外逐字节一致。
- 原文件 SHA-256 前后相同。

当前 BOO 已直接兼容该原包，所以本实验不是新发现一个用户仍打不开的文件，而是证明“规范化结构能让严格 reader 接受原先拒绝的合法图像集合”。这不能证明所有 GM 可读文件都能恢复。

同一实验对 `Mon4024.jpk` 检出了 4 个全零块头和 1 个坏负载，拒绝将它作为无损规范化成功；对 `Mon4028.jpk` 的越界索引也拒绝自动重建。部分图片可预览，与能够完整无损转换是两个结论。

## 推荐的自动处理逻辑

```text
正常读取原包
  ├─ 成功 → 正常显示，不转换
  └─ 失败 → 分类诊断
       ├─ 无密码/密码未验证、未知 profile、IO/权限/运行库错误 → 定向提示，不转换
       ├─ 已知格式且能确定完整原始 ID 映射 → 有边界的恢复读取
       │    ├─ 可直接建立可靠内部索引 → 直接显示
       │    └─ 必须重写布局/封装 → 缓存内规范化副本 → 全量校验 → 正常 reader 重开
       └─ 数据丢失/映射不明 → 明确部分可读或无法恢复，不伪装成功
```

恢复读取不是对失败的 reader 再调用一次。它需要针对已确认的 profile 和故障特征，实现独立的有限候选规则，并生成每个原 ID 到块的可验证映射。存在多种无法排除的候选时停止，不能用“看上去像图片”作为自动编号依据。

自动处理只对已通过密码与 profile 验证、完整槽位可确定的白名单情况启用。遇到局部损坏，可以沿用“正常图片可预览、坏图保留原 ID”的模式，但应明确降级；任何丢图重建/导出必须单独确认。

### 优先直接兼容的原因

如果只是索引后多了一段旧数据，读取器知道有效表就已经能显示，根本不必再复制几 GB 的素材包。规范化副本是兼容后备手段，不应成为所有资源的必经步骤。

如果问题确实在压缩封装，单纯复制压缩块不会修复它；需要已证明可正确解码的有限恢复路径，拿到完整预期长度和像素后，再用标准压缩器重新封装，并逐图校验。不采用“忽略所有解压错误”。

### 副本策略而非覆盖源文件

- 将副本放在 BOO 专用缓存中，原客户端包、Pak.txt/JpkList.txt 和用户配置均不修改。
- UI 继续显示原包名、相对路径、WILL 编号；底层另存 `originalPath` 与 `effectiveReadPath`，原包 SHA 与副本 SHA 分开。
- 缓存身份包含原包内容指纹、精确 profile、规范化规则版本和凭据版本标识；凭据错误或更换后不能盲用旧授权上下文。诊断清单不保存密码或解密状态。
- 正常启动可用 size/mtime 快速检查；生成时、发布前以及明确重载时核验内容指纹。原包变化立即使对应副本失效，不继续显示旧图。
- 在专用进程执行耗时读取/重建，支持取消和进度；同一源包并发请求只启动一个任务，失败不无限循环重试。
- 写临时候选、刷新落盘、校验、原子改名，最后发布清单；失败、磁盘满或取消时不让半成品成为有效缓存。
- 限制文件/槽位/图片大小、解压总量与耗时。大包采用流式复制，不能照搬本轮小样本实验的全文件 Buffer 拼接。
- 只有生成过规范化副本的包增加磁盘占用；缓存淘汰不删除原包，使用中的副本不得被淘汰。活动句柄先释放再清理。
- UI 只显示“正在兼容处理…”、“已兼容，原文件未修改”；具体错误和丢失序号放详情，避免增加大段解释文字。

## 不选的做法

1. **报错后覆盖原文件**：读错 profile 或漏图会直接损伤客户端数据，且很难追溯。
2. **全图导出 PNG 再打包作为默认方案**：不必要地改变像素布局、Alpha、调色板、未知字段和压缩数据，也更慢。可复制的原始块应直接复制；重编码仅用于有证据的必要场景。
3. **扫描图片后顺序编号**：丢失空槽和逻辑 ID，NPC/装备/地图引用会错图。
4. **一律转换成某种 PAK**：破坏引擎/格式分支隔离；插件能显示不代表客户端还能使用。
5. **自动操控原版 GM GUI 作为生产依赖**：当前没有已验证可再分发的命令行/API 合同；安装位置、密码窗、版本、许可和用户交互会影响稳定性。不作为 BOO 的默认依赖。

## 实施优先级与完成门槛

### 第一阶段：错误分类与统一兼容入口

在公共归档层放协调器，补丁管理、预览、地图和 Ctrl+F12 素材消费统一使用。不能只在一个按钮的 catch 中新增功能。区分密码未验证、未知 profile、索引结构、坏负载、IO、缺运行库、取消和资源限制；保留原始错误。

门槛：正确文件不重建；错误密码/权限/缺 DLL 不触发转换；失败最多进入一次兼容流程；更换密码、源文件变化和规则升级可以重新尝试；纯索引成功但懒加载图片失败也有可诊断的逐帧路径。

### 第二阶段：JPK GameLib 规范化

先覆盖已验证 GameLib 结构；996M2 日期变体单独补样本后开放。保留原块、空槽、原 ID、偏移和头部字段。将本轮实验改造成流式、可取消、事务性正式服务，而不是直接接入实验脚本。

门槛：尾段/旧索引/空洞/候选布局测试，以及错误密码、坏负载、越界、源文件中途变化、取消和磁盘满负例。所有正常图记录或必要重编码后的 RGBA/元数据完全一致；零丢图才标无损成功。坏图保留和有损导出是独立模式。

### 第三阶段：GAMEOFMIR / GAMEOFMIR2

复用另一个项目 writer 的格式逻辑，新增允许无编辑规范化的接口；先实现可确定索引的已知结构，分别验证两种签名。重复偏移如果由样本证明是合法共享图片，可在副本展开成独立块但保留每个逻辑 ID；未知头版本不得自动改成 version=2。

门槛：两个真实分支分别通过全槽、空槽、坐标、颜色键/Alpha、像素及正常 BOO reader 重开验证。严格 reader 失败而恢复 reader 成功的真实案例必须有明确映射证据；合成 roundtrip 不替代外部兼容样本。

### 第四阶段：GEEPAK3 main / legacy

分 profile 接入，不把 main 的索引/头规则用于 legacy。保持 legacy 原槽数和能力边界。按像素格式分别验证压缩和透明度，不仅检查“包可以打开”。

门槛：main 和 legacy 各自有真实样本，重建后精确保持逻辑引用；严格读取、缓存、Worker、地图和 NPC 素材输出一致。源码和最终冻结运行时分别验证。

### 第五阶段：GEEPAK2 与未知家族

GEEPAK2 现有读取能力不代表已有同格式 writer；需要独立写入合同与真实样本后再开放。HXM2/LzPak 等缺少已验证生产 reader 的家族不能借自动转换入口宣称支持。

门槛：先取得可验证源语义和格式证据，再开放对应规范化能力。否则保留清晰的未知 profile 提示，并允许用户提供原包/转换后包用于只读诊断。

### 最终集成与交付验收

必须验证原包身份与副本读取路径、WILL/IDX 引用、缓存恢复/失效、取消/并发/清理、大包内存、独立 VSIX 依赖闭包和包内回归；真实 VS Code 中确认原有素材入口能自动继续显示。修改 Python frozen runtime 时，构建和验证最终 bundle 后才能打包。

本轮只新增研究说明和隔离探针，没有生产集成、没有重新打包，没有调用原版 GM 转换，也没有覆盖任何 PAK/JPK。下一步应按上述顺序实施，而非把研究验证宣称为已上线功能。
